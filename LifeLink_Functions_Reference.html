1. Project overview

LifeLink is a web application designed to connect hospitals and blood donors. The front end is mainly built with HTML, CSS, and JavaScript, while the backend is a lightweight Node.js/Express server that stores data in data.json.

The project's core idea is simple:

  • Hospitals can create blood requests.
  • Donors can sign up with blood type information.
  • The system stores users and requests locally and serves them through REST APIs.
  • The user interface updates based on session status and active page state.

The front end is responsible for experience and interaction; the server is responsible for secure storage, authentication, and request management.

2. Frontend structure and lifecycle

The project’s front-end behavior is mostly contained in script.js. It wraps all logic inside an IIFE ((function(){ ... })();) to keep variables local and prevent global pollution.

When the page loads, the script runs:

  1. injectStyles() adds needed CSS to the document.
  2. initNav() creates the mobile menu and scroll behavior.
  3. initActiveLinkTracking() highlights the active navigation item when a section is in view.
  4. initReveal() adds scroll-triggered animations.
  5. initStatCounters() animates the numeric counters.
  6. initUrgentTimestamps() makes urgent request times feel live.
  7. initFooterYear() updates the copyright year automatically.
  8. renderUserIsland() and initAuth() control login and user session behavior.
  9. initHeroAccess() creates a mobile quick-access menu.

The code uses the browser's document, window, and localStorage APIs heavily.

3. Function-by-function explanation in script.js

3.1 injectStyles()

This function creates a <style> tag inside the page head and injects a custom CSS string. It is used to add behavior styles such as:

  • smooth scroll offset
  • header shadow while scrolling
  • active nav link underline
  • mobile nav menu open state
  • reveal animations for sections

It keeps the custom behavior isolated from the main HTML stylesheet so the original design stays clean and modular.

3.2 initNav()

This function sets up the mobile navigation and the header state.

  • It selects the toggle button and nav menu.
  • It sets aria-expanded and aria-controls for accessibility.
  • setOpen(open) toggles the .open class on both the menu and the button.
  • Clicking the toggle opens or closes the menu.
  • All menu links close the menu when clicked.
  • Clicking outside the nav closes it.
  • Pressing Escape closes it.
  • It also adds a header shadow once the user has scrolled down.

Purpose: makes navigation responsive and accessible on smaller screens.

3.3 initActiveLinkTracking()

This function uses the IntersectionObserver API to track which section is currently visible in the viewport.

  • It gathers all nav links whose href starts with #.
  • It maps a target section element to its corresponding link.
  • Whenever a section becomes visible, it removes the active class from all nav links and adds it to the new active one.

Purpose: highlight the current page section while the user is scrolling.

3.4 initReveal()

This function adds the “reveal on scroll” effect using IntersectionObserver.

  • It selects elements such as section heads, steps, rows, and urgent items.
  • Each element gets the .reveal class and a staggered transition delay.
  • If the user has reduced motion enabled, all elements are immediately visible without animation.
  • When an element enters view, it gains .is-visible and the observer stops tracking it.

Purpose: adds polished motion and makes the landing page feel more modern.

3.5 animateNum(el)

This function animates number elements such as “1,000+ donors” or “24/7 support”.

  • It reads the actual text inside the element.
  • It identifies whether the number contains a comma or decimal.
  • It converts the text into a numeric value and animates it from 0 to the target value.
  • It uses requestAnimationFrame for a smooth progression.
  • It re-applies the original formatting at the end.

Purpose: gives the stats a lively, professional presentation.

3.6 initStatCounters()

This function watches the stats container and when it enters the viewport, it runs all the number animations.

  • It looks for the .stats section.
  • It creates an observer.
  • When the stats section is visible, it calls animateNum() for each .num element.

Purpose: triggers animations only when the user sees the stats, which is a good performance pattern.

3.7 initUrgentTimestamps()

This function makes urgent request items show messages like “requested 12 minutes ago” and updates them every minute.

  • It finds all elements with class .urgent-item .sub.
  • It uses a regex to find text such as “requested 2 hours ago”.
  • It converts the value into minutes.
  • Every 60,000 milliseconds, it increases the minutes by 1 and updates the label.

Purpose: creates a realistic live feeling without a real backend timer.

3.8 initFooterYear()

This function updates the footer’s year automatically.

  • It finds the footer text node containing a year.
  • It replaces the year with the current year from new Date().getFullYear().

Purpose: avoids rewriting the year manually every year.

3.9 Local storage helpers

The app uses localStorage for a demo authentication system. These helper functions are essential:

  • getStoredUsers(): reads the user list from localStorage, returning an empty array if the data is invalid.
  • saveStoredUsers(users): saves the array of users.
  • getStoredSession(): loads the logged-in user.
  • setStoredSession(user): stores the active session.
  • clearStoredSession(): clears the session when the user logs out.

Because the project is a demo, localStorage is used instead of a real backend database. This is simple and easy to test, but it is not fully secure for production use.

3.10 isAuthPage()

This checks whether the current page is the authentication page by reading the current page path and comparing it with auth.html.

If the user is already logged in and tries to open the auth page, they are redirected to the dashboard.

3.11 renderUserIsland()

This is one of the most important UI functions. It controls the top navigation user state.

  • It finds the header navigation and CTA area.
  • If no user island exists, it creates one.
  • It reads the current session from localStorage.
  • If there is no user, it shows the normal auth button and hides the user island.
  • If there is a user, it displays a small badge with their role and initials.
  • It changes the button text from “Join LifeLink” to “Open dashboard”.
  • It hides the auth links for logged-in users.

Purpose: creates a dynamic session-aware navigation experience without needing a backend session system.

3.12 initAuth()

This function initializes the entire authentication section on the auth page.

  • If a user is already logged in, it sends them straight to dashboard.html.
  • It finds the auth app container and all tabs/panels.
  • showTab(target) switches between login and signup views.
  • updateRoleFields() shows or hides donor-specific or hospital-specific fields based on the selected role.
  • renderSession() displays the current logged-in user inside the auth page.
  • It wires event listeners for the sign-up form and login form.

The sign-up flow validates:

  • name
  • email
  • password length
  • password confirmation
  • blood type for donors
  • hospital name for hospitals

The login flow checks if the email and password match a saved user in localStorage, then stores the session and redirects to the dashboard.

3.13 initHeroAccess()

This creates a floating menu for mobile hero actions. It is a small UI enhancement.

  • It creates a hidden menu clone.
  • getNavMenuLinks() collects all nav links except the auth page link.
  • syncMenuContent() fills the menu with those links and adds styling.
  • positionMenu() places the menu correctly on mobile or desktop.
  • openMenu() and closeMenu() manage open/closed states.
  • It closes if the user clicks away or presses Escape.

Purpose: improves the mobile experience by giving quick access to top actions, especially on smaller screens.

4. Backend logic in server.js

4.1 Setup and dependencies

The server uses:

  • express for API and static file hosting
  • body-parser for reading JSON request bodies
  • fs for file operations on data.json
  • path for path management
  • crypto for hashing passwords securely

The server itself runs on port 3000 by default, unless an environment variable sets another port.

4.2 readData()

This function reads the JSON file and parses it into JavaScript objects. If the file is missing or invalid, it returns:

{ users: [], requests: [] }

Purpose: keeps the app resilient and prevents crashes on an empty or corrupt file.

4.3 writeData(data)

This writes the full application data back to data.json with pretty formatting.

Purpose: persist user and request information so the app can maintain state between requests.

4.4 hashPassword(password, salt = null)

This function creates a secure password hash using Node’s crypto.scryptSync().

  • If no salt is provided, it generates a random one.
  • It combines the password and salt using scrypt.
  • It returns both the salt and the generated hash.

Purpose: keeps user password storage more secure than plain text storage.

4.5 GET /api/ping

Simple health check endpoint. It returns a basic success message.

Purpose: confirms the backend is running.

4.6 POST /api/signup

Creates a new donor or hospital account.

  • It validates that the required fields are present.
  • It reads the data file.
  • It checks whether the email already exists.
  • If not, it creates a secure password hash.
  • It builds a user object containing role, location, blood type, etc.
  • It saves the user and returns a sanitized payload without password fields.

Important detail: hospital accounts are marked as verified: false, while donor accounts are automatically marked as verified.

4.7 POST /api/login

Authenticates a user by matching email and password.

  • It finds the user by email.
  • It reconstructs the correct hash using the stored salt.
  • If the hash matches, login succeeds.
  • It returns the user object without password details.

Purpose: verifies identity without exposing the actual stored password.

4.8 GET /api/requests

Returns blood requests from the data file with filtering.

  • ?status=open filters by status
  • ?type=blood filters by request type
  • ?place=lagos filters by place text
  • ?hospitalId=... shows requests from a specific hospital

Purpose: helps dashboards and matching screens load only the relevant request data.

4.9 POST /api/requests

Creates a new urgent request.

  • It checks that a type and place are present.
  • It retrieves the hospital user by id.
  • It stores metadata such as hospital name, location, and contact.
  • It creates a request object with a unique id and timestamps.
  • It prepends the request to the data list and saves it.

Important detail: the request is stored with status open by default.

4.10 PUT /api/requests/:id

Updates an existing request.

  • It reads the request id from the URL.
  • It validates the request exists.
  • It updates any field provided in the request body.
  • It enforces valid statuses: open, fulfilled, and cancelled.
  • It updates updatedAt.

The API is flexible because it accepts partial updates without rewriting the whole record.

4.11 GET /api/admin/users

Lists users only if the correct admin key is supplied.

  • It reads key from the query string or x-admin-key header.
  • If the key does not match ADMIN_KEY, it rejects access with 401.
  • It returns sanitized user records without password data.

Purpose: gives the project a thin administrative view without exposing sensitive fields.

4.12 POST /api/admin/verify-user

Allows an admin to verify a hospital or donor account.

  • It checks the admin key.
  • It requires a user id.
  • It finds the account and sets verified to true or false.
  • It saves the updated record.

Purpose: supports a moderation or verification flow for healthcare-related accounts.

4.13 Catch-all route

The final route is a fallback:

app.use((req, res) => res.status(404).send("Not found"));

Purpose: returns a simple 404 when the user requests an invalid URL.

5. How the app works together

The application generally works in this order:

  1. The user opens the site.
  2. The browser loads the HTML and CSS.
  3. script.js initializes the interactive experience.
  4. The user signs up or logs in.
  5. The front end saves the current session using localStorage.
  6. For real API-backed behavior, the Node server reads and writes JSON data.
  7. Hospitals create urgent request objects.
  8. Donors and admins can view or verify records based on role and permissions.

In other words:

  • script.js is the interface layer.
  • server.js is the storage and logic layer.
  • data.json is the data layer.

This arrangement is ideal for a small demo, but not for a production-grade healthcare application, because localStorage and a simple file-based JSON database are not enough for high security or large-scale concurrency.

6. Important developer notes

  • The JavaScript file is mostly UI-driven and browser-based.
  • The backend is intentionally lightweight and educational rather than enterprise-level.
  • Passwords are hashed, but the current project is still a demo.
  • There is no real database, real-time messaging, or live donor matching yet.
  • The design uses local storage for session persistence and quick prototyping.
This project is a strong starting point for a real blood-donation platform, but it would need a real database, stronger security, proper role-based authorization, and more robust validation before production deployment.
